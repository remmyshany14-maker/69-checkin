# 69-checkin

一个基于 **GitHub Actions + Node.js** 的 69 云自动签到项目。配置完成后，GitHub Actions 可以按计划执行签到，并通过邮件发送签到结果；另外还有一个监控工作流，用于提醒当天没有确认签到成功的情况。

> **提醒：** 本项目依赖 69 云网站当前的登录接口和签到接口。若网站改版、接口变化、账号状态异常或 GitHub Actions 未运行，自动签到可能失败。自动化脚本不能替代你定期检查账号状态。

## 功能

- **每日自动签到：** 默认每天北京时间 08:00 运行。
- **签到结果邮件：** 尝试发送签到状态、奖励流量、套餐信息、流量使用情况和运行耗时。
- **失败重试：** 签到流程遇到异常时最多重试 3 次，每次重试间隔 5 秒；最终失败时尝试发送失败邮件。
- **签到监控：** 默认每天北京时间 10:00 检查当天的签到工作流；若没有找到成功的运行记录，会发送异常提醒邮件。
- **仓库保活：** 定时更新 `.keepalive` 文件，增加仓库活动记录，降低因长期无活动导致定时工作流停止的风险；但这**不能保证** GitHub 永远不会停用定时任务。
- **支持手动运行：** 可在 GitHub Actions 页面手动启动签到或测试监控邮件。

## 运行时间

GitHub Actions 的 cron 定时表达式使用 **UTC 时间**：

| 工作流 | UTC 时间 | 北京时间（UTC+8） | 用途 |
| --- | --- | --- | --- |
| Auto Checkin | 每天 00:00 | 每天 08:00 | 执行签到 |
| Checkin Failure Monitor | 每天 02:00 | 每天 10:00 | 检查当天是否有成功的签到工作流 |
| Keep Repository Alive | 每月 1 日和 15 日 00:00 | 每月 1 日和 15 日 08:00 | 更新保活文件 |

GitHub 的定时任务可能延迟启动。监控会根据检查时能查询到的运行记录判断是否成功，因此在签到任务延迟时，仍有可能发出误报提醒。

## 配置指南

### 第一步：Fork 或使用自己的仓库

你可以 Fork 本仓库，或者在自己的 GitHub 仓库中使用这些文件。若 Fork 到自己的账号，请确认工作流文件存在于默认分支中。

### 第二步：添加 GitHub Actions Secrets

进入仓库：

**Settings → Secrets and variables → Actions → New repository secret**

添加以下 5 个 Repository secrets：

| Secret 名称 | 内容 | 用途 |
| --- | --- | --- |
| `USER_EMAIL` | 69 云账号邮箱 | 登录 69 云 |
| `USER_PASSWORD` | 69 云账号密码 | 登录 69 云 |
| `SMTP_USER` | 用于发送通知的 QQ 邮箱地址 | 邮件发件人账号 |
| `SMTP_PASS` | QQ 邮箱 SMTP 授权码 | 邮件发送认证 |
| `TO_EMAIL` | 接收签到通知的邮箱地址 | 邮件收件人 |

**安全注意事项：**
- `SMTP_PASS` 应填写邮箱的 **SMTP 授权码**，不是 QQ 邮箱登录密码。
- 不要把网站密码、SMTP 授权码写进代码、README、提交记录或公开 Issue。
- GitHub Secrets 的值在创建后不会直接显示；如有疑问，可重新设置。
- 如果你使用自己的 Fork，必须在自己的仓库中重新配置这些 Secrets。

### 第三步：确认 Actions 已启用

进入仓库的 **Actions** 页面。如果 GitHub 提示需要启用工作流，请按页面提示启用。然后检查以下工作流是否存在：

- **Auto Checkin**
- **Checkin Failure Monitor**
- **Keep Repository Alive**

如果工作流被禁用，定时任务不会按预期运行。

## 如何手动运行与测试

打开仓库顶部的 **Actions** 页面，选择对应工作流，再点击 **Run workflow**。

### 测试监控邮件

1. 选择 **Checkin Failure Monitor**。
2. 点击 **Run workflow**。
3. 等待运行完成，检查收件箱和垃圾邮件箱。

目前，**手动运行监控工作流会发送一封测试邮件**，用来验证 SMTP 配置；它不会在这次手动运行中检查当天的签到状态。

### 手动执行签到

1. 选择 **Auto Checkin**。
2. 点击 **Run workflow**。
3. 打开本次运行记录，查看各步骤日志和结果邮件。

注意：手动运行 **Auto Checkin 会实际尝试执行签到**，不是单纯的测试操作。不要在不希望执行签到时点击它。

## 邮件通知说明

- 签到脚本会尝试发送签到结果邮件。
- 若签到流程连续重试后仍然失败，脚本会尝试发送最终失败邮件，并让工作流以失败状态结束。
- 监控工作流在当天没有发现成功的签到工作流时会发送提醒邮件。
- **正常情况下，监控工作流不会每天发送“签到成功”的额外邮件。**
- 如果邮箱没有收到邮件，请同时检查垃圾邮件箱、GitHub Actions 运行日志，以及上述 5 个 Secrets 是否填写正确。

监控检查的是 GitHub Actions 的运行记录，而不是独立登录网站再次验证签到状态。如果脚本错误地把网站返回内容判断为成功，监控也可能无法识别实际签到问题。

## 常见问题排查

### 1. Actions 页面没有运行记录

- 确认工作流已启用，且 YAML 文件在默认分支中。
- 查看是否存在最近的仓库提交或其他活动；GitHub 定时工作流可能因仓库长期无活动而被停用。
- 不要只依赖定时运行；可以在 Actions 页面查看状态，并在需要时手动运行。

### 2. 工作流运行失败

打开失败的运行记录，进入失败步骤查看日志。常见原因包括账号密码错误、网站接口变化、网络请求失败或 Secrets 未配置。

### 3. 没收到签到邮件

- 检查收件箱和垃圾邮件箱。
- 确认 `SMTP_USER`、`SMTP_PASS`、`TO_EMAIL` 已设置。
- 使用 **Checkin Failure Monitor → Run workflow** 测试邮件发送配置。
- 如果测试邮件也无法收到，查看该次工作流日志。

### 4. 收到“未确认成功”的监控提醒

打开邮件中的签到运行记录链接，查看当天的 **Auto Checkin** 是否运行、最终状态是否为成功。由于 GitHub 定时任务可能延迟，提醒也可能是暂时的误报。

## 项目文件

```text
.
├── .github/
│   └── workflows/
│       ├── checkin.yml          # 每日自动签到
│       ├── checkin-monitor.yml  # 签到异常监控与邮件提醒
│       └── keepalive.yml        # 仓库活动保活
├── checkin.js                   # 登录、获取信息、签到与邮件通知
├── package.json                 # Node.js 项目依赖
├── package-lock.json            # 依赖版本锁定文件
├── checkin-history.json         # 签到历史数据文件（如项目中使用）
└── .keepalive                   # 保活工作流更新的文件
```

## 技术栈

- GitHub Actions
- Node.js 22
- JavaScript（Node.js 内置 `fetch`）
- Nodemailer（QQ 邮箱 SMTP）
